RayClay patches to the vendored GLFW
====================================

This tree is GLFW 3.5.1 (include/GLFW/glfw3.h, GLFW_VERSION_*), vendored with
the entries below applied. Each edit site in the sources carries a comment
that starts with the marker (the words "RayClay patch", in capitals) followed
by " - " and the entry's family name as its Marker line gives it; a block
closes with "end RAYCLAY PATCH". A vendor bump re-applies every entry, then
holds the markers in the tree and the entries here to the same set.

1. A drag from outside the application is reported while it is over a window.
   Marker: RAYCLAY PATCH - drag-over
   Upstream version: GLFW 3.5.1.
   Files and functions:
     include/GLFW/glfw3.h     GLFWdragfun, glfwSetDragCallback (new)
     src/internal.h           _GLFWwindow.dragOver, callbacks.drag,
                              _glfwInputDrag (declaration)
     src/input.c              _glfwInputDrag (new), glfwSetDragCallback (new)
     src/cocoa_window.m       GLFWContentView.dragOperation, initWithGlfwWindow:
                              (the dragged types), draggingEntered:,
                              draggingUpdated: / draggingExited: /
                              draggingEnded: / wantsPeriodicDraggingUpdates
                              (new), performDragOperation:
     src/x11_platform.h       _GLFWlibraryX11.XdndLeave
     src/x11_init.c           initExtensions (the XdndLeave atom)
     src/x11_window.c         processEvent (XdndPosition, XdndDrop, XdndLeave)
     src/wl_platform.h        _GLFWlibraryWayland.dragFeedback, dragX, dragY
     src/wl_window.c          dataDeviceHandleEnter, dataDeviceHandleLeave,
                              dataDeviceHandleMotion, dataDeviceHandleDrop,
                              _glfwDestroyWindowWayland
   Reason: GLFW reports a drop and nothing before it, so a drop zone cannot
   light up, scroll or refuse while the drag is still over the window, as a
   browser's dragover lets a page do. The patch adds a drag callback: each
   point of a drag over the window arrives with `over` set, in the cursor
   callback's space, and its end once (left, dropped or cancelled), before
   the drop callback when it is dropped. X11 and Wayland report every drag
   over the window, files or not; macOS every drag of files, links or text;
   Win32 reports none. GLFW still accepts and drops only files. The window
   seam hands it on as the `drag` input callback, which RayClay's input
   layer publishes as rci_input_drag. In no released GLFW.

2. nobar's title bar can start an interactive move or resize on Wayland.
   Marker: RAYCLAY PATCH - nobar Wayland interactive move/resize
   Upstream version: GLFW 3.5.1.
   Files and functions:
     src/wl_window.c          glfwWaylandStartWindowMove (new),
                              glfwWaylandStartWindowResize (new)
   Reason: GLFW uses xdg_toplevel's interactive move and resize for its own
   fallback decorations and exports neither. nobar draws RayClay's title bar
   itself and has no wl_seat or input serial of its own, so it delegates a
   drag of the bar and an edge resize to these two entry points, which pass
   the seat and the last input serial GLFW holds; `edge` is an xdg_toplevel
   resize edge. nobar's GLFW glue, inside rayclay.h, declares
   them and compiles their use only where the root CMakeLists.txt marks the
   GLFW it links as this patched tree (RC_GLFW_IS_VENDORED_PATCHED).

3. A quit Apple event ends an application parked in glfwWaitEvents.
   Marker: RAYCLAY PATCH - quit
   Upstream version: GLFW 3.5.1.
   Files and functions:
     src/cocoa_init.m         applicationShouldTerminate: (GLFWApplicationDelegate)
   Reason: a quit that arrives as an Apple event - Dock > Quit, a terminate:
   sent by another process, logout - is handled by AppKit inside the very
   nextEventMatchingMask: call a glfwWaitEvents park sleeps in. The delegate
   marks every window shouldClose and returns NSTerminateCancel, no NSEvent
   is dequeued, and the wait goes back to sleep; an application that polls
   glfwWindowShouldClose after each wait never comes round to read it until
   something else wakes it (a click, a timer), so Cmd+Q, a key event, quits
   at once and Dock > Quit does not. The patch posts GLFW's own empty event
   (_glfwPostEmptyEventCocoa) after the close requests, so the wait returns
   and the next poll sees them. Upstreamable as it stands.

4. A button event on macOS is read where it was made.
   Marker: RAYCLAY PATCH - button point
   Upstream version: GLFW 3.5.1.
   Files and functions:
     src/cocoa_window.m       inputButtonPoint (new); mouseDown:, mouseUp:,
                              rightMouseDown:, rightMouseUp:,
                              otherMouseDown:, otherMouseUp: (GLFWContentView)
   Reason: Cocoa's button handlers pass no point, and the window gets moves
   only while it is key (NSTrackingActiveInKeyWindow) and none for a warp. A
   press with no move before it (the first click on a window that is not key,
   or one synthesized at a new point) was recorded where the pointer
   was last seen, and a drag before the next frame hit-tested it there. Each
   handler now reports the event's own location to the cursor callback before
   the click, as SDL's button event and a browser's mousedown carry theirs. It
   does not go through _glfwInputCursorPos, which drops a point equal to the
   last one it reported: the pointer can leave that point unreported and come
   back, so a press made there went unreported, and an application that had
   polled the pointer elsewhere in between (glfwGetCursorPos) placed the press
   at that poll. A disabled cursor reports deltas and is left alone. A press,
   release and press in one frame gap with the button held at the poll (a
   double click inside one gap) asks for one more frame, at the same point.
   Upstreamable as a new input.c entry that reports a point without the
   dedupe: reporting an unchanged point on each button event is a behavior
   change upstream would have to accept (glfw3.h documents the cursor position
   callback as called when the cursor moves).

5. The XDND replies on X11 carry no stack bytes.
   Marker: RAYCLAY PATCH - zeroed XDND replies
   Upstream version: GLFW 3.5.1.
   Files and functions:
     src/x11_window.c         processEvent (the XdndStatus reply at
                              XdndPosition, the XdndFinished replies at
                              XdndDrop and SelectionNotify)
   Reason: each reply was built as `XEvent reply = { ClientMessage };`, which
   initialises the union's first member, the type, and from GCC 15 nothing
   else: GCC 15 no longer clears the rest of a union an automatic brace
   initializer leaves (-fzero-init-padding-bits=unions restores the old
   behaviour). The data words a reply does not set went to the drag's source
   as whatever the stack held, so an XdndStatus refusing a drag of text,
   which sets neither its accept bit nor its action, read as an accept when
   that stack byte had bit 0 set: an X11 drag-over refusal read as accepted
   in a gcc 15.3.1 Release build with RC_SIZE_OPT and LTO once an unrelated
   change to RayClay moved what the stack held (the refusal's accept word
   measured 0x21). The three replies now start zeroed. sendEventToWM and
   handleSelectionRequest keep the idiom: they set every field Xlib puts on
   the wire. Upstreamable as it stands.

6. glfwInit loads no built-in gamepad mappings.
   Marker: RAYCLAY PATCH - no built-in gamepad mappings
   Upstream version: GLFW 3.5.1.
   Files and functions:
     src/input.c              the include of mappings.h (removed),
                              _glfwInitGamepadMappings (now empty)
   Reason: RayClay reads no joystick or gamepad, and has no API for one, but
   glfwInit parsed all 395 of mappings.h's records into a heap table at every
   start: the 107,478 B of mapping strings in .rodata (8.8 % of a Release
   binary, measured 2026-09-14) and the parsed table on the heap, for a
   lookup nothing makes. The table now starts empty; glfwUpdateGamepadMappings
   still parses mappings an embedder hands it, and joysticks still initialize
   on first use only. mappings.h and mappings.h.in stay in the tree unchanged,
   so a GLFW bump diffs as before; src/CMakeLists.txt's update_mappings target
   still regenerates the header.

7. A key's name on Wayland is NULL, not a crash, on a seat with no keyboard.
   Marker: RAYCLAY PATCH - keyless seat
   Upstream version: GLFW 3.5.1 (upstream's master has no check either, read
   2026-11-08).
   Files and functions:
     src/wl_window.c          _glfwGetScancodeNameWayland
   Reason: the xkb state and keymap are made when a wl_keyboard's keymap
   arrives, so on a seat that advertises no keyboard (a kiosk, a touch device,
   a headless or VNC compositor, CI) both stay NULL, while the scancode table
   is built at init regardless. glfwGetKeyName then reached
   xkb_state_key_get_layout(NULL, ...) and the process died (SIGSEGV): ex06
   resolves its labeled letter keys on its first frame, and segfaulted within
   0.3 s on a keyboardless headless mutter, on NVIDIA and on Mesa (found
   2026-11-08). The name is now NULL until a keymap exists, as
   GLFW documents for a key with no name.

8. Every X11 wait for another client's reply ends.
   Marker: RAYCLAY PATCH - bounded X11 waits
   Upstream version: GLFW 3.5.1 (upstream's master 92dcf4ce has the same
   waits, read 2026-11-12, and still waits on any SelectionNotify, read
   2026-11-13; glfw/glfw#2919 and #2888 are open, and the open pull request
   #2888 bounds the waits with a deadline but still spins on XPending until
   it passes).
   Files and functions:
     src/x11_window.c         waitForX11Event, getSelectionString,
                              _glfwPushSelectionToManagerX11,
                              isSelectionTimeNotify, getSelectionTime,
                              isSelectionReplyTo (new)
     src/x11_platform.h       _GLFWlibraryX11 selectionProperties,
                              selectionNext, GLFW_SELECTION_TIME (new)
     src/x11_init.c           initExtensions (their atoms)
   Reason: waitForX11Event returned the moment any event was queued, and its
   callers each look for one reply (VisibilityNotify after a map, the
   frame-extents reply, SelectionNotify, an INCR chunk), so with any other
   event left in the queue the timeout never ran down, and the selection
   waits had none at all. A window manager that never maps the window (a
   desktop with no output, upstream #2919) held glfwCreateWindow at full CPU
   forever; a selection owner that has stopped answering (#2888) froze a
   paste forever; a stopped clipboard manager kept glfwTerminate from
   returning, so the application could not exit. The wait is now for new
   data on the connection, which every caller's XCheck*Event has just read
   to the end, and bounded: a paste gives up after 0.5 s without an answer
   (each INCR chunk gets 0.5 s), the hand-over to the clipboard manager
   after 0.5 s without a request from it; each failure is a
   GLFW_PLATFORM_ERROR. Reproduced on Xvfb on 2026-11-12 by calling each of
   the three waits: all three hung. A read that gives up
   leaves its request with the owner, which
   may still answer it, during a later read; one property for every request
   let that late answer pass for the later read's: the earlier read's text
   was pasted, or its refusal ended the later read with nothing. Each
   request now names its own property, four taken in turn, and the server
   time it was made at (a zero-length append to GLFW_SELECTION_TIME reports
   it), which the owner copies into its answer (ICCCM 2.2); only the answer
   naming the property, or a refusal naming the time, is taken, and any
   other is dropped. Reproduced on Xvfb on 2026-11-13 with the same calls
   and an owner that answers, or refuses, the first request late, as the
   next one asks. The
   cost: an owner that breaks ICCCM 2.2 and dates its refusal CurrentTime
   instead of copying the request's time has the refusal dropped as another
   request's, so the read waits its 0.5 s and ends with nothing where it
   used to ask for the next target (STRING). The owners vendored here, GLFW's
   handleSelectionRequest and SDL3's X11 one, copy the time. Taking such a
   refusal too would let a late one from such an owner end a later read's
   target, the defect above.
   Upstreamable as it stands.

9. The X11 work area of a monitor just switched off is empty, not a crash.
   Marker: RAYCLAY PATCH - monitor off
   Upstream version: GLFW 3.5.1 (upstream's master 92dcf4ce reads the mode
   unchecked too, read 2026-11-12; glfw/glfw#2883, an open pull request,
   adds the same check).
   Files and functions:
     src/x11_monitor.c        _glfwGetMonitorWorkareaX11
   Reason: a monitor turned off stays in GLFW's list until its RandR event
   is read, and its CRTC then has no mode, so getModeInfo answered NULL and
   the work area read its width through it (SIGSEGV). RayClay reads the work
   area to place every window it opens. It now answers no area and raises
   GLFW_PLATFORM_ERROR, as _glfwGetVideoModeX11 answers no mode for the same
   CRTC. Reproduced on Xvfb on 2026-11-12 by switching the CRTC off from
   a second connection. Upstreamable as it stands.

10. A Wayland keymap does not leak the previous one's compose state.
   Marker: RAYCLAY PATCH - keymap compose state
   Upstream version: GLFW 3.5.1 (upstream's master 92dcf4ce assigns over the
   previous state too, read 2026-11-12).
   Files and functions:
     src/wl_window.c          keyboardHandleKeymap
   Reason: every keymap the compositor sends (a keyboard plugged in again, a
   layout change) builds a compose state from the locale's compose table,
   and the previous state, with the table it holds, was dropped unfreed:
   about 146 KB a keymap for en_US.UTF-8. Measured on a private headless
   mutter 50.6 on 2026-11-12, its RemoteDesktop session plugging a virtual
   keyboard in and out four times: LeakSanitizer counted 439,585 B leaked
   through keyboardHandleKeymap; with the previous state released, none.
   An application running for months on a laptop docked and undocked must
   not grow. Upstreamable as it stands.

11. A Wayland window is focused while the compositor activates it.
   Marker: RAYCLAY PATCH - focus follows activation
   Upstream version: GLFW 3.5.1 (upstream's master 92dcf4ce reports focus
   from wl_keyboard enter and leave only, read 2026-11-12).
   Files and functions:
     src/wl_window.c          xdgSurfaceHandleConfigure, handleConfigure
                              (libdecor), keyboardHandleEnter,
                              keyboardHandleLeave, _glfwWindowFocusedWayland,
                              _glfwHideWindowWayland
   Reason: GLFW reported a window focused only while a wl_keyboard was in
   it, so on a seat with no keyboard (a touch kiosk, a tablet with its
   keyboard detached) a window was never focused, and unplugging the last
   keyboard unfocused the active window: RayClay hid the text caret as if
   the window were in the background, and rcWindowIsFocused, documented as
   the window manager's active window, read false. GTK and Chromium read a
   Wayland window's activation from xdg_toplevel's activated state, and so
   does this now; the keyboard still decides where keys go, its leave from
   a window that stays activated releases the keys held in it, and a
   compositor that never sends the activated state keeps the old rule.
   Measured on a private headless mutter 50.6 with no keyboard, its
   RemoteDesktop session plugging one in and out (2026-11-12): RayClay's
   window read unfocused until the keyboard came and again when it left; now
   focused throughout, keys still delivered. A hidden window (glfwHideWindow)
   is no longer activated: its toplevel is destroyed and no configure follows,
   so the hide clears the state and reports the focus lost (a keyboard still
   in it reports it at its leave). RayClay never hides a window; the clear is
   for the patch to stand upstream.

12. A Wayland seat losing its pointer ends the hover, not the process.
   Marker: RAYCLAY PATCH - pointer unplug
   Upstream version: GLFW 3.5.1 (upstream's master 92dcf4ce releases the
   wl_pointer and nothing else, read 2026-11-12; glfw/glfw#2902 is open and
   its pull request #2914 does the same as this).
   Files and functions:
     src/wl_window.c          seatHandleCapabilities
   Reason: the compositor sends no wl_pointer.leave before it drops the
   pointer capability (the last mouse unplugged, a Bluetooth mouse asleep),
   and GLFW released the wl_pointer but kept the cursor timer, the pointer
   surface and a half-read pointer frame. The cursor timer fires for every
   created cursor whose theme gives its image a delay, which on Fedora's
   stock Adwaita is every standard cursor (one image, 50 ms), so the next
   tick called wl_pointer_set_cursor on NULL: SIGSEGV. RayClay shows the
   hand and I-beam over its controls, so pointing at a button and losing the
   mouse killed the app. The capability loss now disarms the timer, leaves
   the hovered window (the cursor-leave callback fires) and drops the
   pending pointer frame. Reproduced on a private headless
   mutter 50.6 whose RemoteDesktop session unplugged its virtual pointer
   over a window showing GLFW_POINTING_HAND_CURSOR, with the stock theme and
   with an animated one (2026-11-12).

13. A cursor with one image arms no timer on Wayland.
   Marker: RAYCLAY PATCH - static cursor timer
   Upstream version: GLFW 3.5.1 (upstream's master 92dcf4ce arms it for
   every theme image, read 2026-11-12).
   Files and functions:
     src/wl_window.c          setCursorImage
   Reason: setCursorImage armed the cursor timer with the image's delay
   whatever the cursor, and a theme stores a delay on every image: Fedora's
   stock Adwaita gives each standard cursor one image with 50 ms. So while
   the pointer rested on a RayClay control showing the hand or I-beam, GLFW
   woke 20 times a second to set the same image again (a wl_pointer
   request and a cursor-surface commit each), the wake an idle app must not
   make. Measured 2026-11-12 on a private headless mutter 50.6, the
   pointer still over the hand cursor for 7 s: 127 arming timerfd_settime
   calls; now 0. An animated cursor (more than one image) still steps.

14. The items the OS asks the application to open reach a callback on macOS.
   Marker: RAYCLAY PATCH - open files
   Upstream version: GLFW 3.5.1 (upstream's master has no such callback,
   read 2026-11-12 at 92dcf4ce74; its issue 1024 asks for one, open).
   Files and functions:
     include/GLFW/glfw3.h     GLFWopenfun, glfwSetOpenCallback (new)
     src/internal.h           _glfwInputOpen (declaration)
     src/init.c               _glfwOpenCallback, _glfwInputOpen (new),
                              glfwSetOpenCallback (new)
     src/cocoa_init.m         application:openURLs: (GLFWApplicationDelegate,
                              new)
   Reason: macOS hands the files of Finder's Open With and of a drop on the
   Dock icon to the application delegate (an 'odoc' Apple event), at launch
   and while it runs, and a URL of a scheme the bundle declares the same way.
   GLFW's delegate implemented none of it, so AppKit fell back to its document
   controller, which an application with no document classes answers with a
   modal error alert (measured 2026-11-13: a level-8 window, and the app's loop
   held until it was killed), and the items never reached the application. The delegate now
   passes them to a callback, a file as its path and any other URL whole, as
   SDL's delegate does. The callback is a process-wide setter kept outside
   _glfw, like the error callback, because the items that launched the
   application arrive inside glfwInit (_glfwInitCocoa runs [NSApp run] until
   applicationDidFinishLaunching:), so it is set before glfwInit and no GLFW
   function is called from it there. The window seam posts them to the
   queue RC_FILE_DIALOG_OPENED_BY_OS reads.
   Upstreamable as a new callback; other platforms never call it, because
   their OS starts a new process with the paths in its arguments.

15. A Wayland seat losing its keyboard ends the keyboard focus, not later.
   Marker: RAYCLAY PATCH - keyboard unplug
   Upstream version: GLFW 3.5.1 (upstream's master 92dcf4ce releases the
   wl_keyboard and nothing else, read 2026-11-13).
   Files and functions:
     src/wl_window.c          seatHandleCapabilities
   Reason: the protocol does not oblige a compositor to send wl_keyboard.leave
   before it drops the keyboard capability (the last keyboard unplugged, a
   Bluetooth keyboard asleep), and GLFW then released the wl_keyboard but
   kept the window as the keyboard's focus and the key repeat timer armed: a
   key held as the keyboard went kept repeating into the window, read held
   for good, and the window read focused after the compositor activated
   another. The capability loss now runs the keyboard's leave (keys held in
   a window that stays activated are released, the repeat stops, the focus
   follows the activation, patch 11). mutter sends the leave; reproduced
   on a private headless mutter 50.6 through a proxy that
   withholds wl_keyboard.leave and key releases
   (with and without key repeat, 2026-11-13). Upstreamable as it stands.
